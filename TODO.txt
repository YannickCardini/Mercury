[1] BUG — One-frame flash of the hand-cards area when an overlay opens
     (Android native only)
───────────────────────────────────────────────────────────────────────
Symptom
  Tapping the emoji trigger (top-left of the table) or Resign (in the ⋮
  menu, top-right) opens its overlay correctly, but the area BEHIND the
  overlay — the player's hand, i.e. the card fan at the bottom of the
  table — blinks once, briefly, during the opening frame. One blink per
  opening, not a loop. Native Android build only.

Scoping (infer, then confirm with the user)
  The two reported entry points share one mechanism: a full-size
  absolutely-positioned element is inserted at the top of the table's
  stacking context, above the already-rendered hand.
    - emoji trigger → `.emoji-backdrop` (inset 0, z-index 28) +
      `.emoji-palette` (emoji-reactions.component.html:1-3 / 17-30)

    - Resign item   → `.resign-overlay` (inset 0, z-index 200,
      table.component.html:291-306)
  Reaching Resign requires opening the ⋮ menu first, so the user may in
  fact be seeing the flash at the ⋮ step too. Treat all three as the same
  bug; ask the user to confirm whether the ⋮ menu alone already blinks.

Already fixed — do NOT redo
  The older "palette opens → closes → re-opens" double-toggle (Android
  ghost click landing on the freshly-inserted backdrop) is fixed by
  TOGGLE_GUARD_MS (emoji-reactions.component.ts:29-36 and 106-112,
  commit b38bad83). The remaining artefact is a PAINT problem, not an
  event problem: the overlay itself never disappears, it is the content
  behind it that flashes. Confirm this framing before touching event

[2] BUG — Full-board flash when a marble ENTERS the game
     (Android native only)
───────────────────────────────────────────────────────────────────────
Symptom
  During the `enter` animation the whole board blinks for a few frames —
  it looks as if the board/DOM were being reloaded — then everything is
  back to normal. Native Android build only, never on web/desktop.
  It does NOT happen on every enter.

  Narrowed down to ONE action type:
  - Only on `enter` — a marble leaving home for its start square, played
    with a K / Ace / Joker.
  - Never observed on move, capture, swap, promote or discard.

  Ownership bias (the key clue — still unexplained):
  - Happens almost every time the entering marble belongs to the local
    player or to their 2v2 teammate.
  - Not observed when an opponent enters a marble, except once.
  → The mechanism is therefore almost certainly common to every `enter`,
    with something about "my team" entering pushing it over the
    threshold most of the time. Do NOT hunt for a code path that only
    runs for own marbles; look for what makes the same path more
    expensive.

Already tried — did NOT help (do not redo)
  a. fading `.card-selected::after` instead of adding/removing it;
  b. guarding `--square-size` / `calculateSquareSize()` against no-op
     re-writes;
  c. touching `contain` / `backdrop-filter` on `.board-container`
     (native override, board.component.scss:1673-1681).
  Treat these as ruled out as the primary cause.

[3] UX — After the host presses "Start" in a custom room, no player is
     told the game is now searching for the missing players
───────────────────────────────────────────────────────────────────────
Problem
  In a custom (private) room, the host can press "Start" with fewer than
  4 players. The server then closes the room and drops everyone into the
  PUBLIC matchmaking queue, where the empty seats are filled by other
  humans or by AI bots. Nothing in the UI says so — every player is left
  looking at a frozen room screen with no indication that a search is in
  progress, how many seats are still missing, or that strangers/bots may
  join.

What actually happens today (verified in code)
  Server
    backend/src/session/custom-game-manager.ts
      :410-427 startRoomFromCreator() — deletes the room, cancels pending
               invites, then: 4 players → launch() (:444), otherwise →
               fallbackToMatchmaking() (:506).
      :506-527 fallbackToMatchmaking() — every room player is pushed into
               MatchmakingManager.joinQueue(); resolveFallbackColors()
               (:529+) keeps a 2v2 pair together if their colours are
               already taken in the public queue.
    backend/src/session/matchmaking-manager.ts
      :66-136  joinQueue() — assigns/keeps a colour, starts the bot
               dispatch timer, launches as soon as 4 players are present.
      :135-150 tickBotDispatch() — every 1 s, +1 % chance to dispatch an
               external AI agent while a human is waiting.
      broadcastStatus() — sends `matchmakingStatus` (connectedCount,
               totalNeeded, myColor, takenColors) to every queued player
               on every change. So the data needed by the UI is ALREADY
               being pushed to all ex-room players.
  Client — frontend/src/app/home/home.page.ts / .html
      :792-796 startCustomRoom() sets `customStarting = true` → the button
               label becomes "Starting…" (html:1030-1036) and seats stop
               being clickable (selectCustomSlot(), :866).
      :641-680 wireCustomRoomSubs() subscribes to customRoomStatus$,
               gameStarted$, connectionError$, actionRejected$, resumed$ —
               but NOT to matchmakingStatus$.
      Consequences:
        · The room no longer exists server-side, so no further
          `customRoomStatus` arrives → the modal freezes on the last known
          state: room code + copy button (dead code now), stale seats,
          stale "N / 4 players", "Tap an empty seat to choose your team".
        · Non-host players never get `customStarting = true` (host-only
          flag) → their screen does not change AT ALL when the host starts.
        · Their seat taps call sendSelectCustomSlot, which the matchmaking
          listener ignores (it only handles `selectMatchmakingSlot`,
          matchmaking-manager.ts:114-121) → silent no-op.
        · Closing the modal calls cancelCustomGame() (:798-808) which
          sends `leaveCustomRoom` for a room that no longer exists.

Goal
  Keep the server behaviour as-is (the fallback to public matchmaking is
  intentional). Make the transition explicit and correct in the UI, for
  EVERY player in the room, and make the consequence of pressing "Start"
  clear BEFORE it is pressed.

Steps
  1. Before starting — set expectations on the Start button
     (home.page.html:1028-1037):
     · With 4 players: label "Start game".
     · With fewer: label "Start anyway" plus a one-line hint under it,
       e.g. "Missing seats will be filled by other players or AI
       opponents." Show the current count in the label or hint.
     · Fix the dead guard `[disabled]="customRoomPlayers.length < 1"` —
       the list always contains at least the host, so it never disables
       anything. Either drop it or replace it with a real rule
       (`customStarting` only).
  2. Add a third stage to the custom-game modal:
     `customStage: 'choose' | 'in-room' | 'searching'`
     (declared home.page.ts:132).
  3. In wireCustomRoomSubs() (:641), also subscribe to
     `gameStateService.matchmakingStatus$`. On the first message received
     while `customStage === 'in-room'`, switch to `'searching'` and store
     connectedCount / myColor / takenColors into the existing
     matchmaking fields (`matchmakingConnected`, `myMatchmakingColor`,
     `matchmakingTakenColors`, :97-115). This works for the host AND for
     every other player, since the server broadcasts to all of them.
  4. Render the `'searching'` stage. Reuse the existing matchmaking modal
     markup (home.page.html:602-708) rather than duplicating it — extract
     the shared part (title, team seats, "N / 4 players", `.mq-dots`
     spinner, Cancel) into one component or one shared template branch
     used by both `showMatchmaking` and `customStage === 'searching'`.
     In the searching stage:
       · Title: "Finding players…" (same wording as public matchmaking).
       · Hide the room code, the copy button and the invite list — the
         room is gone, the code is no longer joinable.
       · Show explicitly that the remaining seats will be filled by other
         players or AI opponents.
       · Keep the seats live from `takenColors` / `myColor`.
  5. Seat selection in the searching stage must send
     `sendSelectMatchmakingSlot` (as selectMatchmakingSlot(), :583-587),
     NOT `sendSelectCustomSlot` — the latter is silently ignored once the
     room is gone.
  6. Cancel / close in the searching stage must behave like
     cancelMatchmaking() (:565-571): unsubscribe, disconnect, release the
     tab lock, restore presence. It must NOT send `leaveCustomRoom`.
  7. Guard the 4-player case: when the room is full, the server calls
     launch() and `gameStarted$` fires immediately — the searching UI
     must not flash on screen in that case.
  8. Keep the existing background/resume handling working: the resume
     re-join path (:702-725) re-issues `joinCustomRoom` with the stored
     code. Once the stage is `'searching'` that code is dead — the resume
     path must not try to re-join a destroyed room.

Acceptance criteria

  - No server/protocol change is required; if one is added anyway, state
