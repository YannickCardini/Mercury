[1] BUG — Emoji palette blinks once when opened (Android only)
───────────────────────────────────────────────────────────────────────
Symptom
  Tapping the emoji trigger button makes the palette appear, disappear
  and re-appear within a few frames (visible flicker). Happens only on
  the native Android build, not on web/desktop.

Files
  frontend/src/app/game/components/emoji-reactions/emoji-reactions.component.ts
  frontend/src/app/game/components/emoji-reactions/emoji-reactions.component.html
  frontend/src/app/game/components/emoji-reactions/emoji-reactions.component.scss
  Mounted from table.component.html:34 (hidden during the seven-split
  overlay and for spectators).

Leads to investigate (in this order)
  a. Double event on the same tap. `togglePalette()` is bound to `(click)`
     on `.emoji-trigger`; `.emoji-backdrop` (rendered only while the
     palette is open, html:1-3) is bound to `(click)="closePalette()"`.
     On the Android WebView a single tap can produce a second event that
     reaches the freshly-rendered backdrop → close, then re-open.
     Verify whether the sequence is really open→close→open and, if so,
     neutralise it (e.g. stop propagation on the trigger, ignore backdrop
     clicks for a few ms after opening, or drive the toggle from a single
     pointer event instead of `click`).
  b. Animation restart. `.emoji-palette` runs `animation: emojiPaletteIn
     0.15s ease` (scss:74) which starts at `opacity: 0`. If the element is
     removed and re-inserted by the `@if (showPalette())` block, the
     animation replays from opacity 0 → reads exactly like a blink.
  c. Compositing. The palette is an overlay above the board/table; check
     that the native override at scss:163 (backdrop-filter removed) is
     actually applied to the palette on device, and that no parent
     re-creates its compositing layer when the palette mounts.

Acceptance criteria
  - One tap = palette opens once, no intermediate frame where it is hidden.
  - Tapping the backdrop still closes the palette in one tap.
  - Tapping the trigger again while open still closes it.
  - Cooldown behaviour unchanged (COOLDOWN_MS = 2000, trigger disabled
    during cooldown, ts:52-53 / 88-107).
  - Web/desktop behaviour and look unchanged.

[2] BUG — Full-board flash when a marble ENTERS the game
     (Android native only)
───────────────────────────────────────────────────────────────────────
Symptom  (re-scoped after observation on device — this supersedes the
          previous "flashes when a card is played" description)
  The whole board flashes/blinks for a few frames, then returns to
  normal. Native Android build only, never on web/desktop.

  Narrowed down to ONE action type:
  - Only on `enter` — a marble leaving home for its start square,
    played with a K / Ace / Joker.
  - Never observed on move, capture, swap, promote or discard.

  Ownership bias (the key clue — and the part still unexplained):
  - Happens almost every time the entering marble belongs to the local
    player or to their 2v2 teammate.
  - Does not happen when an opponent enters a marble — except once,
    seen a single time.
  → The mechanism is therefore almost certainly common to every `enter`,
    with something about "my team" enters pushing it over the threshold
    most of the time. Do NOT hunt for a code path that only runs for own
    marbles; look for what makes the same path more expensive.

Already tried — did NOT help (do not redo)
  The three leads written in the previous version of this task were
  implemented on device and changed nothing:
  a. fading `.card-selected::after` instead of adding/removing it;
  b. guarding `--square-size` / `calculateSquareSize()` against no-op
     re-writes;
  c. touching `contain` / `backdrop-filter` on `.board-container`
     (native override, scss:1673-1681).
  Treat these as ruled out as the primary cause. Keep whatever cleanup
  was worth keeping, but do not spend time there again.

Leads to investigate (in this order)
  a. marbleDrop animates `box-shadow` — prime suspect.
     @keyframes marbleDrop (scss:220-247) changes `box-shadow` on 4 of
     its 5 keyframes, across the full 800 ms. box-shadow is not
     compositable → the marble is fully repainted on every frame for
     800 ms. It is the ONLY per-marble animation in the stylesheet that
     does this: marbleMove (scss:341-370) and pawnJostle (scss:377-412)
     are transform/opacity/filter only. That alone explains "only on
     enter".
     Worse: `.marble-entering` declares `will-change: transform, opacity`
     (scss:252), which promotes the marble to its own compositing layer
     while the animation keeps dirtying a property that is NOT in
     will-change → the promoted layer is re-rasterised every frame,
     inside a `contain: layout style paint` root.
     Test (native only): keep the transform/opacity part of marbleDrop
     and make the shadow static — or move the drop shadow onto a
     `::after` pseudo-element animated in opacity only.

  b. Compositing layer created then destroyed.
     applyAndWait() (ts:423-436) adds `marble-entering` (with its
     `will-change`) and removes it 800 ms later. Promotion followed by
     demotion inside a `contain: paint` container is a classic Android
     WebView full-repaint trigger, and the 800 ms enter is the
     longest-lived of these layers.
     Test (native only): declare `will-change` (or `translateZ(0)`)
     permanently on `.marble` so no layer is created/destroyed around the
     animation — or drop `will-change` from `.marble-entering` entirely.

  c. The invincibility halo mounts in the same frame as the drop.
     updateMarblePosition() flips `marbleInvincible` to true (ts:696) at
     the exact moment the `marble-entering` class is applied, so
     `.square-invincible` mounts two heavy painted pseudo-elements on the
     destination square: `::before` with a negative inset and three
     box-shadows including `0 0 28px 6px` (scss:1236-1254), and `::after`
     with a conic-gradient (scss:1256-1292). Two large new painted areas
     appearing mid-animation, on top of (a).
     Test: apply the halo only once the enter animation has resolved.
     ⚠️ This also fires for opponent enters, so on its own it does not
     explain the ownership bias — it is an amplifier, not the
     discriminator.

  d. Pin down the real discriminator before assuming "ownership".
     What genuinely differs when the LOCAL player is the one entering:
       - `isCardSelected()` flips to false in the same frame → the
         full-board `.card-selected::after` overlay (62 % black,
         scss:1129-1139) is destroyed, and every native-only
         `.marble-selectable::after` pulse ring (scss:1686-1702) is
         destroyed at once.
       - The entering marble gets `.marble-mine { z-index: 20 }`
         (scss:1141-1143) → new stacking context above that overlay.
       - The card flies `fromHand` (ts:333, 342), with its own overlay.
     None of that applies to the TEAMMATE's turn, yet the teammate case
     flashes too. Two possibilities, cheap to separate:
       1. Positional, not ownership. The board is never rotated — seats
          are fixed (cornerSlots(), ts:928-940: orange=tl, red=tr,
          blue=bl, green=br) and 2v2 teams are red+blue / green+orange,
          i.e. exactly one DIAGONAL of the board each. "My team" and "one
          diagonal of start squares" are indistinguishable from the
          observations so far. If it is positional, look at the drop
          starting at `translateY(-220%)` (scss:222) overflowing the
          square / container differently depending on the corner.
       2. The teammate correlation is a mis-attribution.
     → FIRST ACTION, before writing any fix: ask the user to note the
       COLOUR of the marble that enters each time it flashes (and each
       time it does not), over a few games. Team vs diagonal vs "always,
       just more noticeable sometimes" decides which lead above is right.

  e. Instrumentation (unchanged, still useful).
     `[attr.data-render-tick]="debug ? countBoardRender() : null"`
     (html:2, ts:266-272) tells "the board component re-rendered" from
     "only a repaint happened". If the tick does not move during a flash,
     it is purely a paint/compositing problem → leads a/b/c.

Acceptance criteria
  - Entering a marble (K / Ace / Joker) never produces a full-board flash

Hard constraint
  `BoardComponent.calculateSquareSize()` (board.component.ts:860-873)
  measures `.board-wrapper` via `getBoundingClientRect()` and derives
  `--square-size` **and** `gameStateService.boardContainerSize` (which
  drives the table-wrapper size, game.page.html:64-65).
  → Any change that shrinks the measured wrapper box (e.g. `padding-top`
  on `.board-wrapper`) also shrinks the board and the table. Prefer a
  purely visual offset that does not alter the measured rect:
  for example shifting the board `:host` content down
  (`align-items: flex-end`-style offset, `transform: translateY(...)`, or
  a `margin-top` on `.board-container` rather than on the wrapper).
  If a solution that changes the measured box is chosen, state the
  resulting board-size reduction explicitly before implementing.

Steps
  1. Decide the offset value and express it relative to the free vertical
     space that already exists (the board is `min(w,h) * 0.95` — see
     board.component.ts:865 — so on a portrait phone there is unused
     height above and below it).
  2. Scope the change to the same breakpoint the banner uses
     (`max-aspect-ratio: 12/25`) so tablets/landscape are untouched —
     the banner is hidden there anyway.
  3. Keep the board horizontally centred and keep the four player badges
     in the board corners fully visible (board.component.scss:52-100).
  4. Verify the banner no longer overlaps the top of the board and is not
     clipped by the top of `.game-layout` (which has `padding: 2vh 2vw`
     and `overflow: hidden`, game.page.scss:34-37).

Acceptance criteria
  - Portrait phone, 2v2: visible gap between the banner and the top edge
    of the board; the banner is fully visible.
  - Board size (`--square-size`) and table-wrapper size unchanged, or the
    change is intentional and stated.
  - Landscape, tablets, desktop and 1v1v1v1 mode unchanged.
  - ⚠️ The 820px threshold mentioned in the "mercury-team-vs-banner"
    memory is stale — the real gate in the code is
    `@media (max-aspect-ratio: 12/25)`.
