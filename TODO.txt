=====================================================================
 INFRA — Backend deploys on Azure Web App kill all in-progress games
=====================================================================

## Problem
Every backend deployment restarts the Azure Web App. All game state
lives only in process memory (`GameRegistry`, an in-memory Map —
backend/src/session/game-registry.ts:12 — plus `ReconnectRegistry`),
so every in-progress game is destroyed and players are kicked.
There is currently no SIGTERM/shutdown handler in
backend/src/index.ts.

## Hard constraint
Zero (or near-zero) additional cost. Managed Redis was considered and
rejected as paid.

## Recommended approach: snapshot + rehydrate (no new services needed)
The building blocks already exist:
- Azure Blob Storage is already configured
  (AZURE_STORAGE_CONNECTION_STRING, backend/src/storage/blob.ts) and
  Cosmos DB too (backend/src/db.ts) — either can store snapshots at
  effectively zero cost at current scale; Blob is simpler.
- Clients already auto-reconnect: they persist `guest_player_id` +
  `active_game_id` in localStorage and re-issue `joinGame` with
  backoff (`scheduleRejoin`/`reconnectNow` in
  frontend/src/app/game/services/game-state.service.ts:609-664), and
  the server has a reconnection path (`ReconnectRegistry`, 180 s
  window). If the server can restore games at boot, clients plug back
  in with NO frontend changes.

Steps:
1) Make `Game` serializable: snapshot = players (colors, names,
   userIds, hands, marble positions/invincibility), deck,
   discardedCards, turn/round/currentPlayerIndex/firstPlayerOfRound,
   gameMode, game id (fields listed at backend/src/game/game.ts:35-90).
   Add `toSnapshot()` / `Game.fromSnapshot()`. Exclude transient state
   (pending promises, timers, messenger).
2) Persist: write the snapshot + the ReconnectRegistry entries for
   that game to a Blob container ("games/<gameId>.json") at each end
   of turn, and delete the blob at game end/abort. (SIGTERM-only
   persistence is fragile — Azure's grace window is short and a crash
   gets no signal at all; per-turn writes are tiny and rare.)
3) Restore on boot: load all snapshots, rebuild Game instances in a
   "paused, waiting for reconnections" state, re-register them in
   GameRegistry and ReconnectRegistry, resume the turn loop once
   players rejoin (or let the existing disconnect auto-play/timeout
   logic take over). Discard snapshots older than the 180 s reconnect
   window (or a slightly larger deploy-sized window, e.g. 5 min).
4) Handle non-human seats: external bot agents (dispatched via
   AGENT_URL, backend/src/session/matchmaking-manager.ts:138) will
   not auto-rejoin — decide between re-dispatching an agent for the
   seat at restore, or letting the existing
   disconnected-player auto-play handle them.
5) Verify locally: start a 4-player game, kill and restart the
   backend, confirm all clients reconnect into the same game state.

## Complementary (optional, nice UX)
A pre-deploy notice is still worth having for long maintenance:
a small authenticated admin endpoint that broadcasts "server restarts
in X minutes" to all active games. Do NOT make it the primary
solution — the user explicitly dislikes losing games; it only
softens the edge cases snapshotting can't cover (e.g. schema-breaking
changes where old snapshots must be discarded).
