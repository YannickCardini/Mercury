How to read this file

Global constraints (apply to every task)
- NEVER run the app (no `npm run dev`, no E2E, no screenshots). The
  whole verification loop is: `npm run build:shared` at the repo root
  (mandatory first after any change under packages/shared), the
  `npx tsc` / `npm run build` type checks, and the backend unit tests
  (`npm test --workspace=backend`, node:test through tsx). The backend
  CI workflow builds but does not run the tests. The owner validates
  visually on a real Android device and on desktop.
- backend/src/game/snapshot.test.ts has been seen failing about one run
  in five with "Unable to deserialize cloned data", unrelated to any
  change: rerun it before calling a failure a regression.
- User-facing text: English, neutral tone, never the em dash character.
- Game rules and the shop catalog live in packages/shared so client and
  server cannot drift. Never duplicate an id, a price or a rule in
  backend/ or frontend/.
- Cosmos DB is touched only from backend/src/db.ts, with targeted
  `patch` operations, never read-then-`replace()`. `incr`, `add` and a
  patch `condition` all fail on a field that does not exist yet
  (db.ts:108-116): any new field on the user document needs the same
  kind of guard as ensureWalletFields() (db.ts:126-148).
- Old clients. An installed Android build keeps talking to a newly
  deployed backend until the new build is live on Play and
  LATEST_VERSION_CODE is raised (backend/src/version/
  version-router.ts:16); only then does the app block behind a
  mandatory update popup (frontend/src/app/services/
  app-update.service.ts:56). MIN_VERSION_CODE is served but no client
  code reads it. A browser tab left open also keeps running the old web
  bundle. So every new catalog entry, field or WebSocket message must
  be harmless for the previous build during that window.
- Snapshots. Add only optional fields to GameSnapshot
  (backend/src/game/game-snapshot.ts). Bumping SNAPSHOT_SCHEMA_VERSION
  (:16) discards every in-flight game at the next deploy.
- Android-only rendering fixes go under `:host(.is-native)` at the end
  of the component stylesheet and must leave web/desktop untouched.

[3] FEATURE - Shop bonus: double all coins earned for one week
     (price: 50 coins)
───────────────────────────────────────────────────────────────────────
Owner's note (verbatim)
  "Ajoutez un bonus dans le shop qui permet de doubler toutes les
  pieces gagnés pendant une semaine (prix: 50 peices)"

Goal
  A time-limited pass: for 7 days after purchase, every coin credited
  at the end of a game is doubled. Not to be confused with the existing
  "Double Coins" booster (10 coins, one game).

Open questions (ask first)
  Q1. Label. It must not be mistaken for "Double Coins".
  Q2. Stacking with the per-game Double Coins: ×4, or ×2 at most? If
      ×2 at most, should the shop refuse to arm Double Coins while the
      pass is running?
  Q3. Buying again while it is active: refused (assumed) or extended by
      7 days?
  Q4. Which instant decides: the moment the coins are credited, i.e.
      game end (assumed, simplest), or game start?
  Q5. Should the pass be visible during a game (boost dock), or only in
      the shop, on the home page and on the end screen?

Facts
  - Coins are credited in one place: applyEndGamePoints(),
    game.ts:1462-1508. Amount = computeEndGameCoins(victory, captures,
    multiplier) (coins.ts:22-24): victory coins (winners only, 1 to 8,
    computeWinCoins() :12-15) plus Bounty coins, times the Double Coins
    multiplier. "All coins earned" therefore means that sum. The debug
    credit route (shop-router.ts:134-154) is not a gain.
  - The per-game model (`armedBoosts`, emptied by consumeArmedBoosts()
    when a game starts) does not fit a duration. The pass needs its own
    field on the user document, for instance an expiry timestamp. Dates
    are stored as ISO 8601 UTC strings, which compare chronologically
    (db.ts:335-336).
  - Atomic purchase patterns already in db.ts: one conditional patch
    (purchaseItem(), :222-247) or read + etag retry
    (consumeArmedBoosts(), :264-290). Mind the absent-field rule.
  - applyEndGamePoints() already reads each participant's document once
    (getUserPointsAndRanking(), game.ts:1438-1443): return the expiry
    from that same read instead of adding a round trip.
  - The purchase route picks the inventory field from
    isConsumable(item) (shop-router.ts:87-88) and answers with
    `coins, ownedItems, armedBoosts` (:95-100). GET /state returns the
    same plus the catalog (:55-60). The client mirrors that in
    ShopService and caches it in localStorage under `shop_state`
    (shop.service.ts:15-21, 188-226), cleared on sign-out.
  - End screen: the "Double Coins" seal and the doubling animation are
    driven by `gameStats.boosts` (victory-overlay.component.ts:116,
    177-193, 264-275). With only the pass active that list is empty:
    without a change the screen would show a doubled total with no
    explanation and a breakdown that does not add up.
  - User document types are declared twice (backend/src/auth/
    auth-router.ts:58-82, and frontend auth.service.ts /
    profile.page.ts).

Steps
  1. Shared: catalog entry at 50 coins with its duration as a named
     constant, and one pure helper answering "is the pass active at
     time T", used by both sides. Decide between a new ShopItemKind
     (recommended: the booster texts "Applies to your next game only"
     and "Next game" are wrong for a pass) and a flagged consumable.
  2. db.ts: the expiry field, its guard, an atomic purchase function,
     and the expiry returned with the wallet.
  3. shop-router.ts: a purchase branch for the pass, the expiry in both
     responses, an explicit error code when it is already active.
  4. game.ts: apply the pass multiplier where coins are computed,
     according to Q2 and Q4, and tell the client through an optional
     GameStatsMessage field.
  5. Frontend shop: tile state "active, N days left", confirmation
     text, ShopService and its cache. Home page: an indicator next to
     the existing booster strip (home.page.html:96-108).
  6. End screen: seal and doubling animation for the pass.
  7. Tests: coins.test.ts (pass alone, pass + Bounty, pass + Double
     Coins per Q2), shop-catalog.test.ts, and the "active at T" helper
     at the boundary.

Acceptance criteria
  - Buying costs 50 coins once, atomically: it can never drive the
    balance below zero, nor be charged twice by two concurrent
    requests.
  - From purchase until exactly 7 × 24 h later, every end-of-game coin
    credit is doubled, Bounty coins included, whoever receives them.
    After that, credits are back to normal with no action needed.
  - Expiry is decided by the server clock only.
  - The shop and the home page show that the pass is active and until
    when; the end screen shows why the amount was doubled.
  - Guests and AI-agent seats are unaffected.
  - The per-game Double Coins behaves as today when no pass is active.

Goal
  Every admin alert sent to Telegram also says, about the player it

    a. New account. backend/src/auth/auth-router.ts:181, inside

    b. A human joins the public matchmaking queue.
       backend/src/session/matchmaking-manager.ts:133-149, in

  What the server already receives, with no client change
    Origin   Read for the allowlist (backend/src/index.ts:42-55, 152).

    browser requests desktop sites announces itself as a Linux
    desktop. Both are reported as desktop; only the client can tell
    them apart.
  What the client knows
    Capacitor.getPlatform() / isNativePlatform() are used across the
    frontend (auth.service.ts:73, app-update.service.ts:42). No

    JoinMatchmakingMessage (packages/shared/src/types.ts:411-425) is

    (verifyTokenWithServer(), auth.service.ts:125-135).

Steps
  1. Backend: a small pure helper (suggested: backend/src/admin/

  2. Sign-up alert: build the label from `req.headers` and append it
     to the Telegram text and to the console.log just above it
     (auth-router.ts:180-181).
  3. Matchmaking alert: record the label once per socket where `req`
     exists (index.ts:151), in a WeakMap keyed by the socket, and read
     it in joinQueue() when the text is built
     (matchmaking-manager.ts:133-136). Do not add an eighth positional
     parameter to joinQueue().
  4. Only if Q1 = the client declares its device: an optional field on
     JoinMatchmakingMessage and in the sign-up body, filled by one

     expected enum values, prefers them over the header guess, and
     falls back to the headers when the field is absent (old builds).
     Run `npm run build:shared` first.
  5. Tests: a node:test file next to the helper (model:
     backend/src/session/guest-tracking.test.ts) covering the app on a
     phone, the app on a tablet, Chrome on Android, Safari on iPhone,
     an iPad, a desktop browser, and missing headers.

    deliberately sends the name and not the email
    (auth-router.ts:179). Send the short label only: never the raw
    User-Agent, never the IP address.
  - Headers are written by the client. Assemble the label from fixed
    words, never from header text.
  - Append to the existing message. A second message per event would
    halve the budget of 20 per minute.
  - Guest branch: compute the label before the asynchronous lookup,
    not inside its callback.

Acceptance criteria
  - Both alerts end with the client and the device type, in the
